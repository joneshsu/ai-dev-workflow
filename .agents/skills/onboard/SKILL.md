這是一個已經存在、但還沒有導入 AI 開發流程的專案。請協助我把這套流程導入，並且**以專案現有的做法為準**，不要把範本的預設值強加給專案。

## 原則
- 整個過程**不修改任何程式碼**，也不重新整理既有檔案。
- 範本與專案現況衝突時（例如 commit 格式、目錄名稱、測試工具），**以專案現況為準**，並把衝突列出來讓我決定。
- 推測出來的內容要標示「推測」，經過實際執行或我確認的才算定案。

## 步驟

### 1. 唯讀探索
閱讀以下內容（存在的才讀），了解專案現況：
- `README`、既有文件、`CONTRIBUTING`
- 套件與建置設定（如 `package.json`、`pyproject.toml`、`go.mod`、`pom.xml`、`Makefile`、`Dockerfile`）
- CI 設定（如 `.github/workflows/`）、lint 與格式化設定
- 目錄結構與主要模組、進入點
- 測試：使用的框架、測試放在哪裡、大致涵蓋哪些部分
- `git log`：近期 commit 訊息的格式、最常被修改的檔案（通常是核心或高風險區域）

### 2. 驗證指令
找出安裝、建置、測試、lint、啟動的指令，並實際執行確認是否可用。
- 會安裝大量套件、連線外部服務、修改資料庫或耗時很久的指令，**先問我**再執行。
- 測試若本來就有失敗，**只記錄、不修正**，作為之後的基準線。

### 3. 回報現況
用條列整理給我看：
- 技術棧與版本
- 已驗證的指令（標示成功／失敗）
- 目錄結構與主要模組的職責
- 觀察到的程式碼慣例（命名、錯誤處理、分層方式等），並附上代表性的檔案作為例子
- commit 訊息目前的格式
- 測試現況：哪些區域沒有測試或測試不足
- 高風險區域：修改頻繁、複雜度高、沒有測試的部分
- 你不確定、需要我回答的問題
- 範本與專案現況的衝突清單（例如：專案已有 `docs/` 且用途不同、commit 格式不是 Conventional Commits）

**等我確認並回答問題之後**，再進行下一步。

### 4. 寫入文件
1. 更新 `AGENTS.md`：
   - 「目前階段」改為「階段 3：功能開發中」
   - 填入專案概要、技術棧、主要目錄、**已驗證**的常用指令
   - 「程式碼慣例」填入觀察到、並經我確認的現有慣例
   - 依我對衝突清單的決定，調整「開發流程」中的規則（例如 commit 格式改為沿用專案原本的格式）
   - 若有已知會失敗的測試，記錄在「已知問題」區塊，並註明不要順手修改
2. 撰寫 `docs/project/02-architecture.md`，標題註明「現況架構（as-is）」，描述**目前**的架構，而不是理想的架構。不確定的部分標示「推測」。
3. 若專案沒有說明用途的文件，可以撰寫精簡的 `docs/project/00-vision.md`；PRD 與 roadmap 不需要補寫。
4. 對於從程式碼中看得出來的重大技術決策（例如選用的框架、資料庫），可以撰寫 ADR，狀態標示「已接受（追溯記錄）」。只寫真正重要的，最多 3～5 份。

### 5. 建議下一步
提出 2～3 個建議的第一批任務，優先考慮：
- 為高風險且缺乏測試的區域補上 **characterization test**（描述現有行為的測試），讓之後的修改有安全網
- 一個小而明確的功能或 bug 修正，用來完整試跑一次 spec → plan → implement → review 流程
