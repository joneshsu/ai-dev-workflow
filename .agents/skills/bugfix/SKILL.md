description: 處理已合併或已發布功能中發現的 bug：重現、寫出失敗的回歸測試、找出根本原因、最小修正，並記錄在 docs/bugs/。在使用者回報 bug 或要求修 bug 時使用。

使用者回報了一個 bug（內容附在呼叫此 skill 時的訊息中，可能包含錯誤訊息、log、重現步驟或 issue 連結）。請依照以下流程處理。

## 0. 分流：先判斷要走哪條路
- **正在開發中、尚未合併的功能出錯**：不需要這個流程，直接在 implement 的當前步驟中修正。告訴我後就結束。
- **修正需要改變設計、影響多個模組，或其實是需求沒想清楚**：先完成步驟 1～3 的調查，再建議我改走 spec → plan 流程，並把調查結果寫進新的 spec。
- **線上緊急問題（hotfix）**：可以先修正、後補紀錄，但回歸測試不能省略。
- 其他情況：繼續以下步驟。

## 1. 釐清與重現
1. 若資訊不足（預期行為、實際行為、重現步驟、環境、版本），先問我，一次問最關鍵的問題。
2. 找出相關的 spec（`docs/specs/`）與 ADR，確認「預期行為」到底是什麼。若 spec 沒有定義這個情況，告訴我，由我決定正確的行為。
3. 在本地重現問題。**無法重現就不要開始修改程式碼**，回報你嘗試過的方式，並說明還需要什麼資訊。

## 2. 寫出失敗的回歸測試
寫一個能重現這個 bug 的測試，執行並確認它**因為這個 bug 而失敗**（不是因為其他原因）。
這個測試之後會永久保留，防止同樣的問題再次發生。

## 3. 找出根本原因
- 先列出可能的原因假設，再逐一用證據（閱讀程式碼、加 log、git log／git blame、縮小範圍）驗證或排除。**不要憑猜測修改程式碼。**
- 區分「症狀」和「根本原因」。例如：「回傳 null」是症狀，「快取過期時沒有重新載入」才是原因。
- 檢查同樣的錯誤模式是否也出現在其他地方。
- 向我簡短報告根本原因與修正方向，**等我確認後再修改**。若是很小、很明確的問題，可以在報告中直接附上修正的 diff 一起確認。

## 4. 最小修正
1. 只修改解決根本原因所需的程式碼，**不要順手重構或修改無關的地方**。
2. 確認回歸測試通過，再執行完整測試、lint 與型別檢查。
3. 用 `fix:` 類型 commit（例如 `fix(cart): reload price when cache expires`）。若有 issue 編號，寫在 commit 訊息中。

## 5. 記錄與回饋
1. 依照 `docs/bugs/_template.md` 寫入 `docs/bugs/YYYY-MM-DD-<kebab-case-標題>.md`。一行就能修好的小問題可以省略，只靠 commit 訊息記錄。
2. 若是 spec 的驗收標準漏掉這個情況，**建議**我在對應的 spec 補上一條驗收標準（經我同意才修改）。
3. 若在步驟 3 發現其他地方有相同的問題，列出來，建議另外處理，不要在這次一起修。
4. 若這個 bug 是 AI 產生的程式碼造成的，而且是可能重複發生的模式，建議一條可以加進 `AGENTS.md` 的規則。
